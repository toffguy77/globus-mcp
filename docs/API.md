# Внутреннее API online.globus.ru

Swagger/OpenAPI сеть не публикует. Всё ниже — результат ручной разведки: каждый
эндпоинт и формат тела проверялся на живом API, парсеры прогонялись на реальных
фрагментах ответов. Документ описывает то, на что опирается `globus_mcp/client.py`,
и может устареть в любой момент.

## Топология

```
online.globus.ru  →  www.globus.ru            Next.js SSR, отдаёт HTML и /_next/data
                     digitalone.globus.ru     BFF, отдаёт JSON
```

Базовый URL BFF: `https://digitalone.globus.ru/d1-front-bff/api-web/v1`

## Заголовки

| Заголовок | Обязателен | Смысл |
|---|---|---|
| `X-App-Id` | да | UUID устройства. К нему привязаны корзина и контекст получения. |
| `Authorization: Bearer <JWT>` | нет | Без него сессия анонимная. |
| `Content-Type: application/json` | да для POST/PATCH | |

**Без авторизации API работает.** Поиск, каталог, карточки, акции и даже корзина
доступны анонимно. Токен нужен только для `checkout`, истории покупок и адресов
доставки. Это ключевое свойство: сервер полезен сразу после установки.

## Формат ответа

Всё завёрнуто в конверт:

```json
{ "data": { … }, "errors": [] }
```

`errors` может быть непустым **при HTTP 200** — это всё равно ошибка. Клиент
разворачивает конверт и поднимает `GlobusError` в обоих случаях
(`GlobusClient._unwrap`).

**Все цены — в копейках**: `12999` == 129,99 ₽.

## Контекст получения

`purchase_method` определяет цены и наличие:

| Значение | Способ | Обязательное поле |
|---|---|---|
| `1` | самовывоз из гипермаркета | `store_id` |
| `2` | доставка по адресу | `address_id` |
| `3` | пункт выдачи | `pvz_id` |

Меняется через `PATCH context` с телом `{"context": {"purchase_method": 1, "store_id": 7}}`.

**`GET/POST basket*` требуют "онлайн"-контекст** — `purchase_method` `2` (доставка)
или `3` (ПВЗ). При `purchase_method: 1` (самовывоз из гипермаркета) любой запрос к
корзине падает с `400 Online context required`.

## Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| POST | `catalog/search:result` | поиск: `{query, sort, include:["products"], pagination}` |
| POST | `catalog/search:preview` | подсказки поиска |
| POST | `catalog:product-list` | товары категории — **двоеточие после `catalog`, не слеш** |
| POST | `catalog/filters` | фильтры категории |
| POST | `header` | меню каталога и мини-корзина: `{include:["dropdown","menu","basket"]}` |
| GET / PATCH | `context` | текущий способ получения и его смена |
| GET | `directories/stores` | справочник гипермаркетов |
| GET | `directories/pvz` | справочник ПВЗ |
| GET | `basket` | корзина |
| POST | `basket:update-products-quantity` | добавить/изменить/удалить (`quantity: 0`) |
| GET | `checkout` | данные оформления (401 без авторизации) |
| GET | `content/pages/{code}` | CMS-страницы (`divorce_shares` — акции) |
| POST | `content/product-tapes` | ленты рекомендаций |
| GET | `operation-history/operation-list` | справочники + список операций (заказы, начисления/списания бонусов); требует авторизации |
| GET | `operation-history/details-online/{order_id}` | детали онлайн-заказа: статус, доставка, адрес ГМ, история статусов **и состав заказа** (`data.products.categories[].product_list[]`); требует авторизации |
| GET | `operation-history/details-offline/{purchase_id}` | детали покупки в гипермаркете: магазин, дата, скидка **и состав покупки** (`data.product_departments[].product_list[]`); `purchase_id` — составной id из `gm_data` (см. ниже), не число; требует авторизации |
| POST | `catalog/you-bought-set` | «уже покупали»: `{sort, include:["products"], pagination}`, тот же групповой формат товаров, что в каталоге; требует авторизации |
| POST | `catalog/favorite-products` | список избранного: `{sort, pagination}`, тот же групповой формат товаров; требует авторизации |
| GET | `catalog/favorite-id-products` | массив id избранных товаров — лёгкая проверка «в избранном ли»; требует авторизации |
| POST | `catalog/favorite-products:mass-add` | добавить/убрать из избранного: `{"products":[{"product_id": "...", "is_favorite": true\|false}]}`, отвечает `{"data": null}`; требует авторизации |

Пагинация `operation-history/operation-list` — курсор `last_operation_date`
(дата последнего заказа с предыдущей страницы, `YYYY-MM-DD`), а не `page`.
Подтверждено на живом API.

Каждый месяц в `grouping_data[]` несёт два независимых списка:
`order_data` — онлайн-заказы (те же, что видны через `order_details`), и
`gm_data` — покупки в гипермаркете (самовывоз/на месте, без доставки). Отдельного
параметра фильтра не существует и не нужен — оба списка приходят в одном ответе.
Параметр `operation_category` (по значениям из `filter_data.operation_category`)
проверен и **не работает** — API его молча игнорирует.

Запись в `gm_data` устроена иначе, чем в `order_data`: `id` — составной слаг вида
`5019_52_347_71_2026-06-12_18:26:27` (использует сайт для своей страницы), а не
числовой номер заказа. В `operation-history/details-online/{order_id}` он не
принимается — но для него есть свой эндпоинт, `details-offline` (см. выше);
`order_details` в `server.py` сам выбирает, какой из двух дёрнуть, по наличию `_`
в переданном id.

Как и любой авторизованный ответ BFF (см. «Скользящее обновление» в разделе
«Авторизация»), ответ `details-offline` тоже содержит поле `id_token` — свежий
JWT текущего пользователя. Наружу из инструмента его отдавать нельзя (см. «ПДн
наружу не вываливать» в CLAUDE.md) — `order_details` его не трогает, выбирая
только нужные поля; сам токен подхватывает `GlobusClient._unwrap`.

### Сортировка

`default`, `price_asc`, `price_desc`, `discount_desc`, `name_asc`, `name_desc`.

### Пагинация

`{"pagination": {"page": 1, "per_page": 20}}`. `per_page` до `100` работает.

### Фильтры каталога

Передаются как `{"filter": {"filter": ["3:17134"]}}` — пара
`<id фильтра>:<id значения>`.

* `3:17134` — бренд Parmalat;
* у флаговых фильтров значение — буквально `да`: `2147483644:да` (только со скидкой);
* фильтр типа `1` — диапазон (цена), у него `min_value`/`max_value`.

Строки собирает инструмент `category_filters` — вручную их конструировать не нужно.

## Детальная карточка товара (SSR)

В BFF её нет. Данные берутся из Next.js:

```
GET https://www.globus.ru/_next/data/<buildId>/products/<slug>.json?productId=<slug>
```

`buildId` вытаскивается регуляркой `"buildId":"([^"]+)"` с главной страницы,
кешируется на 15 минут и **перечитывается при первом 404** — после деплоя сайта
старый `buildId` перестаёт существовать.

Внутри ответа полезное лежит в дегидратированном состоянии react-query:

```
pageProps.dehydratedState.queries[] → queryKey содержит "product-detail" → state.data.product
```

Это делает `GlobusClient.query_data(next_json, "product-detail")`.

## Авторизация

Двухшаговый вход по SMS через Next.js API-роут на `www.globus.ru`, не через BFF:

```
POST https://www.globus.ru/api/oauth/login   {"phone": "79161234567"}          → SMS
POST https://www.globus.ru/api/oauth/login   {"phone": "...", "code": "1234"}  → access_token
```

**Первый шаг подтверждён** — запрос без `phone` отвечает `400 phone field required`.
**Второй шаг угадан и не проверен на живом входе.** Если формат ответа отличается,
рабочий обходной путь — забрать JWT из авторизованного браузера:

```js
__NEXT_DATA__.props.pageProps.token
```

и передать в `auth_set_token`. Срок жизни токена — около часа (`exp` в JWT).
Подпись клиент не проверяет: payload декодируется только чтобы показать, кто вошёл.

**Скользящее обновление.** Любой авторизованный ответ BFF несёт в конверте не
только `data`, но и `id_token` — свежий JWT (не только при логине).
`GlobusClient._unwrap` подхватывает его и тут же сохраняет через `set_token`.

**`exp` в JWT не авторитетен для реальной валидности.** Проведен эксперимент с использованием API:
токен успешно принимался спустя 9+ часов после собственного `exp`. Судя по
всему, сервер ориентируется не только на время, но и на `sid` (claim в JWT, id сессии
конкретного входа) — валиден **последний** выданный токен в цепочке ротации
этого `sid`, независимо от часов. Как только где-либо (в браузере, мобильном
приложении, другом вызове MCP) с тем же `sid` сделан новый запрос, все более
старые копии токена этой сессии сразу становятся недействительны (`401
Unauthenticated`) — даже если их `exp` ещё не наступил.

Из этого следует: параллельная работа с одной и той же сессией из браузера и
через MCP-сервер конфликтует — они перетирают токен друг у друга. У разных
устройств/входов (`auth_set_token` с JWT от нового логина) — свой `sid`, свой
независимый токен, друг другу не мешают. **Практический вывод**: для токена,
который передаётся в `auth_set_token`, стоит логиниться в приватном окне
браузера (не в основной сессии пользователя) и не пользоваться этим окном
параллельно ни для чего другого — так `sid` останется исключительно за MCP и
никто (ни сам пользователь в обычном окне, ни мобильное приложение с тем же
логином через тот же idp) не перетрёт токен своей активностью.

Наша проверка `token_expired` в `globus_status`/`auth_set_token` (сравнение
`exp` с текущим временем) поэтому лишь эвристика: она может ошибочно считать
токен ещё живым, если его уже инвалидировали параллельной активностью, и не
отличает эту причину сбоя от настоящего часового тайм-аута простоя.

## Как проверять изменения

Юнит-тесты офлайновые и живой API не покрывают. Если правите транспорт, прогоните
инструменты руками с российского IP:

```python
from globus_mcp.server import search_products, product_details
print(search_products("молоко", per_page=3))
print(product_details("<url из результата выше>"))
```
